In design · v2 · prototype + architecture · Aug 2026

One prediction pool app for every sport your group follows.

Predictopia v1 shipped in a 9-day solo sprint as an IPL-2026-only app — then sat dormant nine months a year by design. That scoping mistake became the v2 thesis: a Group (persistent people) / Pool (tournament instance) split and a generic prediction-event model, so cricket, football, or the next sport a family adds all run through one schema. Currently a full clickable prototype validating the PRD before a line of v2 backend code gets written.

The Problem

v1 worked. Then cricket season ended.

v1 was a genuine success at family scale — one-tap picks, auto-lock before toss, on-demand scoring, offline prize tracking, built solo in 9 days on Next.js + Supabase. But it was hardcoded to IPL 2026: the schema, the copy, the scoring rules all assumed cricket, one tournament, one window each year. Outside March–May, the app — and the family habit around it — just stopped.

📅

~9 months dead time/year

A tournament-bound app is only as alive as its tournament. The real product opportunity was multi-sport, year-round — v1's scope was the bug, not the build quality.

🔁

Every new season = re-invite everyone

v1 conflated "the people" with "the season." A new pool meant a new link, a new round of WhatsApp invites, and starting the group's trust graph from zero.

🧩

One-off event types don't scale

Special contests ("who makes the Top 4?") would have needed their own bolted-on data model per sport if outcomes and specials weren't unified from day one.

How It Works

Group and Pool are two different lifetimes — the schema finally says so

The core v2 move: separate "the people" from "the tournament instance." A Group is created once and persists — a family, a college WhatsApp circle. A Pool is a specific competition running under that Group, and reuses the Group's membership automatically. New Pools stop requiring new invites; new Group members aren't retroactively dropped into pools already mid-season.

1

Group created once

"The Family" — persists forever, membership is durable across every future tournament.

Result

No re-invite tax. A second Pool under the same Group needs zero new links shared.

2

Pool = one tournament instance

"Family Cup — IPL 2026," "Office Banter — EPL 25/26." Opt-in per Pool, never auto-enrolled.

Result

Someone in the Group can skip a sport they don't follow without it reading as a dead leaderboard slot.

3

Every prediction is a generic "event"

Question + answer format + point value + resolve state — one structure for match outcomes AND admin-authored special events.

Result

Admin-authored specials shipped in MVP with zero schema rework, because the model was built to support them from day one.

Who It's For

Two roles, one design north star

Primary

The Pool Admin

Usually the one who set up the WhatsApp group in the first place

Creates the Pool, sets buy-in and prize splits, pushes specials, closes periods. If admin pain is eliminated, the pool survives — every design decision optimises for their workload approaching zero after setup.

Secondary

The Member

Wants to predict, see the board, and get their money — nothing else

One-tap picks, cutoff countdowns, a Board that's never cluttered with admin actions, and a Money tab that's honest about what they're owed and what's settled.

Technical Depth

Portable by design, not vendor-locked

Same free-tier-until-traction discipline as the rest of this portfolio: Postgres + app-owned domain logic, auth mapped to an internal user id rather than a vendor's, sports data behind a swappable provider adapter.

Stack

Next.js + Supabase, kept from v1

Next.js (App Router) PWA Auth.js — Google only Supabase Postgres + RLS Vercel + GitHub Actions cron CricketData + API-Football

Domain/schema rewrite matters more than an infra change. Auth.js + portable GUC identity (not auth.uid). Jobs via GitHub Actions for sub-daily reminders. See architecture diagrams.

Data model

Group / Pool / generic event

Group → persistent people Pool → tournament instance Event → outcome | special (question, answer format, points, resolve state)

Outcomes and admin-authored specials are instances of one structure — the thing that let specials ship in MVP with no schema change.

Access control

Hybrid RLS + API routes

Auth.js → app.user_id GUC RLS → membership + reveal Jobs → app_jobs + JOB_SECRET DB → lock triggers

Reveal of others' picks is an RLS rule after lock — not UI-only. Cutoff enforced by DB trigger. Full path on the identity diagram.

Key Decisions

A sample of 50+ logged, dated, with reasoning

The full decision log runs to over fifty dated entries — including several reversals, kept visible rather than silently rewritten. A representative sample:

Architecture

Group vs. Pool split

v1 conflated people with season. v2: Group persists, Pool is a tournament instance under it, reusing Group membership automatically.

Data model

Generic "event" for outcomes and specials

One structure, not two — the reason admin-authored specials shipped in MVP with zero schema rework.

Scoring

One running total; periods are a filter

Admin can pay out at arbitrary intervals without a separate ledger — period leaderboards are a lens over the same per-event records.

Money

Tracking only, never a payment gateway

Buy-in and prizes settle offline (UPI/cash) — app shows Collected/Not-collected and Owed/Settled, never moves money itself.

Trust

Group join is the vetting gate, not Pool opt-in

An admitted stranger gets standing access to the whole Group across every future Pool — so the admit/deny gate moved to match, off the old v1 per-pool approval model.

Navigation

Reveal folded into Board, Money promoted to a tab

Freed a tab slot without exceeding five — full navigation/IA redesign, discussed and locked before building, shipped 2026-08-06.

Correctness

Tie-split budget bug, caught and fixed

An external review pass caught a "shrink" tie rule that could overspend the prize pot — corrected to a budget-safe formula before it reached build.

Scope

Pool creation restricted to Group Admins

Reversed an earlier "any member can create a Pool" call once real financial terms (buy-in, fee %, prize splits) were in scope — the Group Admin who vets membership should also see a Pool's economics before it goes live.

Out of Scope

Scope defence is a product skill

CutWhy
In-app paymentsApp tracks buy-in/prizes offline; a real payment gateway is a different regulatory and engineering surface entirely.
Group-level money rollupMoney stays Pool-scoped in MVP — a Group aggregate view across every Pool under it is a deliberate v2.1 cut, not an oversight.
Push notificationsNo notification channel exists yet — Profile ships opt-in toggles now so the preference exists before the channel does.
Public pool discoveryAll v1/v2 pools are private, invite-only. Search/browse only makes sense once enough pools exist to browse.
Numeric-distance stat predictionsConsidered for things like "guess the number of sixes" — rejected: needs a scoring curve per stat plus tie-break logic, and reads too fantasy-sports-adjacent next to the real-money legal question.
