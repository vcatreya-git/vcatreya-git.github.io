PMRocket — Career Navigation for Aspiring PMs

A market-grounded career navigation platform for Product Managers.

Version 2.5 Updated 2026-07-18 Active Stack: Vercel + Neon + Clerk + Vercel AI SDK (V3.0)
Section 1

Executive Summary

Product
PMRocket
One-liner
A market-grounded career navigation platform that maps aspiring Product Managers to the right PM role, builds a personalised evidence roadmap calibrated against real job descriptions, and tells them — with market evidence — when they are ready to apply.
Problem in a nutshell
Aspiring PMs spend 6–18 months in a directionless preparation loop because no platform tells them which PM role fits their background, what specific evidence to build, or when they are ready to apply. 40% of candidates fail at the recruiter screen due to lack of domain depth — the exact gap every existing platform ignores.
Solution
A five-stage intelligence pipeline: (1) 15-question intake; (2) weighted scoring model matching to PM archetype; (3) three-layer curriculum kept current via JD-derived ETL; (4) RAG-powered gap analysis vs real JD requirements; (5) market-grounded readiness signal with ready-to-apply gate.
Target user
The Wanderer — aspiring PM, 3–6+ months prep, directionless. Secondary (V2a): The Navigator — existing PM levelling up or switching domain.
Key outcome
≥15% cold application-to-recruiter-screen conversion for users who apply to archetype-matched roles after completing a full PMRocket readiness pathway (vs ~3% cold application industry baseline — a 5× improvement).
Market
North America first (personal use, alpha); India second.

The Core Problem

Aspiring PMs cannot navigate the PM career transition because the preparation landscape is fragmented, generic, and disconnected from what employers actually screen for. No existing platform tells a candidate which PM role fits their specific background, what domain-specific evidence to build for that archetype, or when they are genuinely ready to apply.

Root Causes

Root CauseDescription
Supply calibrated to old hiring bar40% rejected at recruiter screen for domain depth (Mind the Product, 2025). All major prep platforms teach PM frameworks that companies used to test for. Employers have moved; platforms haven't.
No navigation layerEvery platform assumes the candidate already knows which PM role to target. None performs background-to-role matching.
No credible readiness signalExisting readiness scores use internal rubrics with no connection to what employers actually require. "You're at 62" means nothing without market grounding.
Evidence-building not taughtEmployers require portfolio evidence: PRDs with success metrics, A/B test documentation, domain analyses. Platforms teach frameworks to talk about evidence without building any.
Geography-blind preparationFintech PM in India needs UPI/RBI/NPCI knowledge. Fintech PM in US needs ACH/OCC/Dodd-Frank. No platform adapts preparation to target geography.

Why Now

  • AI compression at junior tier — Entry-level PM tasks are being automated; the floor for real evidence over framework familiarity is rising.
  • India GCC expansion — 1,750+ GCCs in India, 75%+ managing AI/digital products by 2026 (Zinnov). Specific archetype with no platform support.
  • Post-layoff talent flow — 55,875 US tech layoffs YTD March 2026. Engineering-to-PM transitions are accelerating.
  • AI PM role explosion — 300% growth in AI PM postings since 2023. Specific, testable technical bar — no platform prepares candidates.

score(A) = Σ[w×raw] / Σw across all signals; admin-configurable weights

Section 6

Weighted Matching Model

V2 replaces the V1 decision table with a weighted scoring model. Every intake signal contributes a score for every archetype; the archetype with the highest total weighted score wins.

Formula

score(A) = Σ [ weight(q, A) × raw_score(q, A, answer(q)) ] ───────────────────────────────────────────────────── Σ weight(q, A) for all questions q where the user has answered

Example — Technical PM archetype

QuestionWeightAnswerRaw ScoreContribution
Q1 background8"Software Engineer / Backend"1.08.0
Q12 tech skills (avg of 5 sub-skills)9avg(Strong, Expert, Practised…) = 0.80.87.2
Q7 domain4"B2B SaaS"0.83.2
Σ = 21score = 18.4 / 21 = 0.876

Weights are admin-configurable via the question_weights table — no code deployment required. Tie-breaking: if two archetypes score within 0.02, Q12 (technical skills) absolute contribution decides. The runner-up becomes adjacent_archetype_id.

Evidence Levels

Completion level is auto-computed from topic_progress JSONB — never manually selected:

  • Learning — any Learning-tier topic checked
  • Practised — all Learning topics complete + any Practised topic checked
  • Mastered — all Practised topics complete + any Mastered topic checked

Tier unlock triggers a celebration animation. The Mastered tier is portfolio-quality: the user could teach the skill.

Section 8

Gap Analysis (RAG Pipeline)

On-demand RAG pipeline. User taps "Analyse my gaps." System retrieves the top-25 JDs from the pgvector HNSW index matching their archetype × domain × geography profile. LLM generates:

  • gap_pct — artefacts with evidence / total artefacts in roadmap
  • Top 3 skill gaps — with recommended artefacts from the curriculum
  • Qualitative narrative — "Based on 23 Fintech PM JDs in the US, here are your top 3 gaps…"

Corpus Gate

Gap analysis button is hidden if fewer than 15 JDs exist for the user's archetype × domain × geography slice. Placeholder: "We're building the JD corpus for your market — check back soon."

Ready-to-Apply Gate

gap_pct <= 30% AND no critical skill gaps → "Your gap analysis shows you're ready to apply."
Section 9

Evidence Logging

  1. 1. User selects artefact from roadmap or Evidence picker (bottom nav)
  2. 2. Modal opens — progressive topic tiers: Learning (open), Practised (locked until Learning complete), Mastered (locked until Practised complete)
  3. 3. Completion level auto-computed from tier coverage — user never selects a level manually
  4. 4. Optional: description (200 chars) + supporting link (auto-prefixed with https://)
  5. 5. Save → topic_progress JSONB updated → gap analysis re-runnable → activity timeline entry appended

Self-attestation evolution: V2a is self-reported (gap analysis communicates this clearly). V2b adds peer evidence review. V3 adds AI artefact critique against the archetype rubric.

Section 13

Ethical Risks & Mitigations

⚠ Risk 1 — Readiness signal miscalibration

If the JD corpus for a given archetype × domain × geography slice is small or skewed, the gap percentage may over- or under-represent actual market requirements. A user could be told they are "ready to apply" when their evidence is insufficient for the broader market — or the reverse.

Mitigation
Gap analysis only available when corpus ≥20 JDs per slice (increased from display threshold of 15). Admin dashboard shows corpus size per slice. Gap analysis output always shows "Based on N JDs" — user sees the evidence base. Admin can pause gap analysis for any suspect slice.

⚠ Risk 2 — Archetype matching bias

Initial weights are editorial estimates, not empirically calibrated. The model may systematically favour one archetype over others until user data validates the weights.

Mitigation
Archetype distribution monitored as a success metric — no single archetype should capture >50% of active users. If any archetype exceeds 60%, a weight calibration review is triggered. Admin can adjust weights at any time. Users can switch archetypes freely via the Archetype Explorer.

⚠ Risk 3 — Self-attestation gaming

Users can check all topic checkboxes to reach "Mastered" without actually building the evidence. This drives gap_pct to zero through dishonest logging.

Mitigation
This is an explicit V2a design choice. The incentive structure works in the user's favour — gaming only harms their own preparation. The UI communicates clearly: "Gap analysis is based on your self-reported evidence against real JD requirements." V2b adds peer evidence review; V3 adds AI artefact critique. The product never claims verified readiness.
Section 14

Definition of Done (Alpha — thin demo slice)

The Alpha targets one archetype × one domain × North America on the free-tier V3 stack. Done when:

  • New user can complete the full hero flow: sign-up → intake → archetype match → roadmap → evidence log → readiness signal — without error
  • Intake state is saved on exit; user resumes from the correct question on return
  • Evidence logging updates the readiness signal immediately and displays the delta
  • Archetype switch recalibrates roadmap and readiness signal without data loss
  • Admin can edit seed artefact content and matching weights without a code deployment
  • Migrations run clean on a fresh Neon database (migration runner tested end-to-end)
  • Local: npm run dev serves the full hero flow with real auth and real data
