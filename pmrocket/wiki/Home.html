PMRocket

A career navigation platform for aspiring Product Managers. Turns preparation into a market-grounded journey from confusion to confident readiness.

What is PMRocket?

PMRocket solves the navigation problem every aspiring PM faces: infinite content, zero direction.

You've read the books. You've watched the videos. You've built case studies. But you don't know if you're building the right things for the role that fits you. You don't know when you're actually ready to apply. The existing platforms teach frameworks generically; PMRocket is a layer underneath: which role, what proof, when you're done.

The product works in five stages:

  1. Intake (3 minutes): Fifteen questions about your background, skills, and goals
  2. Archetype match: Weighted scoring model reveals which PM role fits you best (Technical, Growth, Enterprise, AI)
  3. Personalised roadmap: Three-layer curriculum (universal skills, archetype-specific, domain-specific)
  4. Evidence logging: Track progress as you build artefacts through progressive tiers (Learning → Practised → Mastered)
  5. Market-grounded readiness: Gap analysis against real job descriptions tells you where you stand

As a portfolio project, PMRocket demonstrates:

Problem framing: The discovery phase validated that navigation, not content, is the unmet need. This wasn't assumed—it was researched, tested against alternatives, and defended against a discovery reviewer.

Persona-driven design: Every feature exists for one person—The Wanderer, an aspiring PM 3-6 months into self-directed prep. Scope is defended by that lens, not by feature lists.

Market-grounded product decisions: The readiness signal isn't invented—it's built from real job descriptions. The matching model is weighted, not editorial. The curriculum evolves from an ETL pipeline that reads actual hiring requirements.

Honest scope discipline: The roadmap explicitly states what's in v1 (matching + roadmap + readiness), what's deferred (interview practice, coaching), and why. No feature creep.

Production-grade SaaS thinking: Free-tier hosting doesn't mean toy shortcuts. Auth, ownership checks, migrations, error handling, and honest readiness metrics are built from day one. The roadmap shows a clear transition path to AWS when traction justifies it.

What makes it technically interesting

Weighted archetype matching

The archetype matching model treats every intake response as a scored signal for every PM archetype. Fifteen signals are grouped into five categories — background, experience, skills, domain, and goals — and each signal carries a configurable weight per archetype stored in a question_weights table. The matching formula is a normalised weighted sum: score(A) = Σ[weight × raw_score] / Σweight across all answered signals. A software engineer answering Q1 scores 1.0 for Technical PM and 0.3 for Consumer PM; the same Q1 for a finance background inverts those scores. Q12 (technical skills self-rating) carries the highest weight (9) for Technical PM and Platform archetypes; Q13 (product skills) and Q14 (business skills) carry higher relative weight for Consumer and B2B archetypes. Tie-breaking uses Q12 absolute contribution when two archetypes score within 0.02 of each other. Weights are admin-configurable at runtime — no code deployment required. The model is deterministic and market-grounded, not editorial.

Progressive artefact tier unlocking with computed evidence

When a user logs evidence for an artefact, the system automatically splits the artefact's key_topics[] into three equal-size tiers (Learning/Practised/Mastered). The evidence modal presents progressive checkboxes for each tier; completing all checkboxes in Learning automatically unlocks Practised. This approach means no manual tier progression logic — the tier structure is derived from topic completion percentages. The topic_progress JSONB column tracks which topics the user has marked across all evidence logs for an artefact. Completion percentage triggers tier unlock: Learning (0–33%), Practised (34–66%), Mastered (67–100%). Tier animations celebrate promotion and unlock premium features.

Readiness score computation with self-healing

The system computes and updates readiness scores via a deterministic pipeline: computeAndSaveScore(userId) aggregates evidence, applies per-category rubrics (e.g., Technical artefacts worth 8 pts each, Portfolio artefacts worth 5 pts each), multiplies by completion tier (Learning = 0.5× multiplier, Practised = 0.8×, Mastered = 1.0×), and saves the total to readiness_scores via UPSERT. When a user logs evidence (POST /api/evidence-log), the route awaits score computation synchronously — no fire-and-forget callbacks. The readiness GET endpoint is self-healing: if no score row exists for a user, it computes on demand. This prevents stale or missing readiness data even if the webhook or async job fails. The radar chart on the Readiness page visualises the score breakdown by category.

pgvector HNSW gap analysis with deterministic gap_pct

Gap analysis uses a retrieval-augmented generation pipeline against a live corpus of embedded job descriptions. When a user triggers gap analysis, the system embeds their profile (archetype + domain + geography + skill signal) using text-embedding-3-small (1536 dimensions) and queries the jd_embeddings table via pgvector cosine similarity with K=25 retrieval. The HNSW index is built with m=16, ef_construction=64 — sufficient for high recall at the JD corpus sizes PMRocket targets. Retrieved JDs are passed with the user's evidence log to the LLM, which produces a qualitative narrative and identifies the top three skill gaps with recommended artefacts from the curriculum. Alongside the narrative, a deterministic metric is computed: gap_pct = (1 − evidenced_artefacts / total_artefacts) × 100. The gap analysis button is hidden if fewer than 15 JDs exist for the user's archetype × domain × geography slice — the product never generates a signal from an insufficient corpus.

LLM abstraction layer

All LLM calls — ETL skill extraction and gap analysis narrative — route through a factory pattern that decouples the application from any specific provider. getLLMModel() reads the ACTIVE_LLM_PROVIDER environment variable and returns the appropriate Vercel AI SDK model instance: Groq (Llama 3.3 70B, free tier, default), Anthropic (Claude Sonnet 4.6), or Google (Gemini 2.0 Flash). getEmbedModel() follows the same pattern via ACTIVE_EMBED_PROVIDER. Switching providers requires one environment variable change and no code changes. This matters for a free-tier portfolio project: Groq runs inference free, but the abstraction means the same code runs in production on Anthropic or Google without modification. The ETL extraction prompt is constrained to the existing skill taxonomy vocabulary — the LLM cannot introduce new skill terms, only map JD text to known taxonomy entries.

Admin ETL pipeline

The admin surface is the editorial engine that keeps the curriculum market-grounded without requiring a code deployment. An admin pastes raw JD text into the ingestion UI; the system calls the LLM extraction endpoint (POST /api/extract-skills), which strips the JD of PII, identifies skills, and maps each to the existing taxonomy vocabulary. The admin reviews the extracted skills in a queue UI — accepting, rejecting, or editing each mapping — and approves the batch. On approval (POST /api/confirm-extraction), the system embeds the full JD via text-embedding-3-small, writes the embedding to jd_embeddings, updates the artefacts table where new skills warrant curriculum changes, and triggers POST /api/aggregate-skill-frequency to recalculate skill_frequency for the affected archetype × domain × geography slice. The admin Curriculum Signals panel surfaces Trending skills (high JD frequency, not yet in curriculum), Stable skills, and Declining skills — actionable without touching code.

Navigation system with UserMenu

The frontend now uses a unified AppNav component that renders the PMRocket logo, a personalized greeting with the user's first name ("Hi, {name} 👋"), and a three-dot UserMenu across all pages. The UserMenu component is a shared dropdown containing email, "Retake assessment," and "Sign out" — with an extraItems prop for page-specific menu additions. This centralised navigation reduces duplication and ensures consistent brand presence. The BottomNav component provides 4-tab navigation: Home | Roadmap | Readiness | Apply (locked). Archetype selection moved to the greeting click → Profile modal.

Node.js migration runner

The database schema is managed by 18 pure PostgreSQL SQL files applied in numeric order via a custom Node.js migration runner at scripts/migrate.ts. There is no Supabase CLI dependency, no ORM, and no framework magic. The runner connects to Neon via @neondatabase/serverless, creates a migrations table on first run to track applied filenames, reads all .sql files from the migrations directory, compares against the applied set, and runs each unapplied migration inside a transaction — failure rolls back the transaction and halts the runner with a clear error. This approach keeps the migration story portable: the same runner works against any PostgreSQL-compatible database, which matters for the planned Vercel → AWS ECS Fargate transition at product phase.

Clerk TEXT user IDs

The V3 architecture replaced Supabase Auth with Clerk, which required a non-obvious schema change: users.id is TEXT, not UUID. Clerk user IDs follow the format user_2abc... — they are not UUIDs. Every foreign key referencing users.id across the schema is therefore TEXT, and every WHERE user_id = $userId query in API routes uses the string value from Clerk's auth() call. User rows are provisioned via a Clerk user.created webhook (POST /api/webhooks/clerk) that inserts into users, user_profiles, and subscriptions in a single transaction. To handle the edge case where the webhook fires late or fails, every authenticated API route that touches user data includes a lazy provision check: if the user row is missing on a valid Clerk session, it is created before the business logic runs.
