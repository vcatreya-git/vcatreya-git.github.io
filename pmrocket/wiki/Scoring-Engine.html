Scoring Engine

The readiness score is the quantitative signal that answers "when is this candidate genuinely ready to apply?" It is computed deterministically by aggregating evidence completion, weighted by artefact category rubric and completion tier.

Score Computation Pipeline

When a user logs evidence for an artefact via POST /api/evidence-log, the request:

  1. Validates the artefact exists and belongs to the user's roadmap
  2. Persists the evidence entry into the evidence_log table
  3. Updates the artefact's topic_progress JSONB with checked topics
  4. Synchronously calls computeAndSaveScore(userId) — no fire-and-forget
  5. Returns the updated evidence entry and the new readiness score
// POST /api/evidence-log
export async function POST(req: Request) {
  const { userId } = auth()
  if (!userId) return new Response('Unauthorized', { status: 401 })

  const { artefactId, tier, description, link, topic_ids } = await req.json()

  // 1. Validate and persist
  const evidence = await db.insertEvidence({ userId, artefactId, tier, ... })

  // 2. Update topic_progress
  await db.updateTopicProgress(userId, artefactId, topic_ids)

  // 3. Compute and save score synchronously
  await computeAndSaveScore(userId)  // Awaited — blocks until complete

  // 4. Return result
  return Response.json({ evidence, readiness_score: await getReadinessScore(userId) })
}

This synchronous pattern ensures the readiness score is always fresh after any evidence change. The user sees an accurate readiness update before the response completes.

computeAndSaveScore() Function

Located in src/lib/scoring.ts, this function:

  1. Fetches all evidence entries for the user
  2. Groups evidence by artefact category
  3. For each artefact with evidence, multiplies base points by completion tier multiplier
  4. Sums the weighted points across all categories
  5. UPSERTs the total into the readiness_scores table
// src/lib/scoring.ts
export async function computeAndSaveScore(userId: string) {
  // 1. Fetch all evidence for the user
  const evidence = await db`
    SELECT DISTINCT ON (artefact_id)
      a.id, a.category, a.max_points,
      e.tier, e.created_at
    FROM evidence_log e
    JOIN artefacts a ON e.artefact_id = a.id
    WHERE e.user_id = $userId
    ORDER BY a.id, e.created_at DESC
  `

  // 2. Compute score
  let totalScore = 0
  const categoryScores = {}

  for (const log of evidence) {
    const tierMultiplier = {
      'Learning': 0.5,
      'Practised': 0.8,
      'Mastered': 1.0
    }[log.tier] || 0.5

    const points = log.max_points * tierMultiplier
    totalScore += points
    categoryScores[log.category] = (categoryScores[log.category] || 0) + points
  }

  // 3. Save to readiness_scores
  await db`
    INSERT INTO readiness_scores (user_id, total_score, category_breakdown, computed_at)
    VALUES ($userId, $totalScore, $categoryScores, NOW())
    ON CONFLICT (user_id) DO UPDATE
    SET total_score = EXCLUDED.total_score,
        category_breakdown = EXCLUDED.category_breakdown,
        computed_at = NOW()
  `

  return totalScore
}

Artefact Tiers and Key Topics

Every artefact has:
- max_points: base points awarded when Mastered (e.g., 8 for Technical, 5 for Portfolio)
- key_topics: array of 15 learning topics (5 per tier: Learning/Practised/Mastered)

When logging evidence, the modal auto-splits key_topics[] into three equal-size tiers by dividing by 3:

Tier Topics Completion %ile
Learning topics[0:5] 0–33%
Practised topics[5:10] 34–66%
Mastered topics[10:15] 67–100%

The user checks boxes for topics they've covered. Completing all checkboxes in Learning automatically unlocks Practised. Completion percentage determines progression:

  • Learning complete: 5/5 topics checked (100% of Learning tier)
  • Practised unlocked: at least 1 Practised topic checked (>0% of Practised tier)
  • Practised complete: 5/5 Practised topics checked
  • Mastered unlocked: at least 1 Mastered topic checked
  • Mastered complete: 5/5 Mastered topics checked

This design means:
- No manual progression logic — tiers are computed from topic coverage
- Users see granular progress (topics) mapped to readable tiers
- The modal naturally guides progression

Category Rubric and max_points

Artefacts are grouped into five categories with differing max point values:

Category max_points Why Examples
Technical 8 High signal of readiness for technical-heavy roles Write 10 SQL queries; Build a simple API; Read system design paper
Business 6 Medium signal; helps all archetypes Analyse 3 financial statements; Build a pricing model; Study TAM methodology
Portfolio 5 Required for credibility; lower complexity Create a case study; Maintain a blog; Document side project
Domain 7 Archetype-specific depth Study fintech regulation; Learn B2B SaaS GTM; Understand enterprise sales cycles
Product 6 Core PM skills Run 5 user interviews; Write 3 specs; Conduct competitive analysis

Total possible score for a user with all evidence logged at Mastered: (8 + 6 + 5 + 7 + 6) × 1.0 = 32 points (for thin slice seed data).

Self-Healing Readiness GET

When a user requests their readiness (GET /api/readiness), the endpoint:

  1. Queries for an existing readiness_scores row
  2. If found, returns it
  3. If not found (webhook delay, job failure, etc.), synchronously computes the score on demand
  4. Returns the freshly computed or cached result
// GET /api/readiness
export async function GET(req: Request) {
  const { userId } = auth()
  if (!userId) return new Response('Unauthorized', { status: 401 })

  // 1. Try to fetch existing score
  let score = await db`SELECT * FROM readiness_scores WHERE user_id = $userId`

  // 2. If missing, compute on demand
  if (!score) {
    await computeAndSaveScore(userId)
    score = await db`SELECT * FROM readiness_scores WHERE user_id = $userId`
  }

  return Response.json(score)
}

This pattern ensures no user ever sees "no score available" or stale data — the system self-heals latency and failure modes.

Tier Multipliers and Scoring Strategy

The tier multiplier (0.5 / 0.8 / 1.0) encodes a philosophy:

  • Learning (0.5×): Basic familiarity. You've read the material, taken notes, or completed a tutorial. Valuable as a start, but insufficient for a job interview.
  • Practised (0.8×): Applied experience. You've run one or two examples, built a small project, or explained the concept to someone. You can defend it in conversation.
  • Mastered (1.0×): Interview-ready. You've repeatedly applied the skill, can debug problems, and can teach others. You own the concept.

A user logging all evidence at Learning (0.5× tier) reaches ~31% readiness. Progressing the same evidence to Practised (0.8×) reaches ~50%. Reaching Mastered (1.0×) unlocks the ready-to-apply gate at 62%+.

This multiplier design means:
- Quantity alone (many Learning artefacts) is not sufficient
- Quality/depth (advancing to Mastered) is required for readiness
- The gap_pct + readiness score together create accountability (can't game readiness by rushing through Learning)
