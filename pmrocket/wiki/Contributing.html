Local Dev Setup

# Clone the repo
git clone https://github.com/vcatreya-git/pmrocket.git
cd pmrocket

# Install dependencies
npm install

# Set up environment variables
cp .env.example .env.local
# Fill in all required keys — see Environment Variables below

# Run migrations against your Neon database
npx tsx scripts/migrate.ts

# Seed initial content
npx tsx scripts/seed.ts

# Start the development server
npm run dev

The app will be available at http://localhost:3000.

Clerk webhook in local dev: Clerk webhooks require a publicly reachable URL. Use the Clerk CLI tunnel or ngrok to expose your local server:

# Option A: Clerk CLI tunnel
npx @clerk/local-tunnel

# Option B: ngrok
ngrok http 3000

Point the Clerk webhook endpoint to https://<your-tunnel-url>/api/webhooks/clerk.

Running Migrations

The migration runner applies SQL files from supabase/migrations/ in order. It tracks applied files in a migrations table and wraps each migration in a transaction. Re-running is safe — already-applied files are skipped.

npx tsx scripts/migrate.ts

If you add a new migration file, name it with the next sequential number prefix (e.g. 019_...sql) and re-run the command. Only the new file will be applied.

Coding Standards

TypeScript

Strict mode is enabled everywhere. No any in committed code. Prefer interface over type for object shapes. Use const assertions for static maps (e.g. archetype configurations).

Error handling

API errors always return { error: { code: string, message: string } }. Validation errors include a fields map. LLM errors return 502 with code LLM_ERROR — never expose provider error details to the client. Log full context server-side; return a generic message to the client.

Logging

Structured JSON: { level, timestamp, message, context }. Log at: API route invocations (input/output summary), all errors with stack traces, auth events, admin mutations, LLM calls (latency + token count — never prompt content or JD text).

Never log: passwords, session tokens, full email addresses outside auth context, Stripe secrets, raw JD text, API keys.

Auth

Every protected route calls auth() from @clerk/nextjs/server before any database access. Missing session → 401 immediately. Ownership violations → 403. Admin role check failures → 403 (not 404 — the route exists, the user just lacks permission). Include WHERE user_id = $userId on every user-scoped database query without exception.

No Vercel-specific primitives

Never import from @vercel/edge, @vercel/kv, @vercel/blob. Never use export const runtime = 'edge'. All routes must run identically on any Node.js host — this is the Docker portability guarantee.

File naming

Kebab-case for files, PascalCase for React components, camelCase for functions and variables.

Import order

React / Next → external libraries → internal modules → types → styles.

Key Architecture Constraints

These constraints exist for specific reasons. Changing them requires a Decision Log entry.

  1. users.id is TEXT, not UUID. Clerk user IDs are user_2abc... format. Every FK to users.id is TEXT.
  2. No Vercel Edge Runtime. All routes use default Node.js for Docker portability.
  3. LLM and embed calls go through getLLMModel() / getEmbedModel(). No direct SDK imports in route handlers.
  4. Readiness score is computed synchronously on evidence log. POST /api/evidence-log awaits computeAndSaveScore(userId) before responding. No fire-and-forget async jobs.
  5. gap_pct is computed by application code, not the LLM. The LLM provides qualitative output only. Formula: (1 - evidenced_artefacts / total) × 100.
  6. No query returns another user's data. WHERE user_id = $userId is mandatory on all user-scoped queries, even with a valid session.
  7. Artefact key_topics must be exactly 15 items. The evidence modal auto-splits into three equal tiers (5 topics each). Schema-enforced via migration.
  8. Score self-heals on GET. If readiness_scores row is missing, GET /api/readiness computes on-demand. No "no score" state visible to users.
