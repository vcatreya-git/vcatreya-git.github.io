Stack Decision

The stack is split into two phases that share identical application code. The switch from personal to product phase is infrastructure configuration only — no code changes — because the app is Dockerised from day one and uses no Vercel-specific primitives.

## LLM Abstraction

All LLM and embedding calls go through a provider factory in `src/lib/llm.ts`. Switching providers requires no code changes — only the `ACTIVE_LLM_PROVIDER` or `ACTIVE_EMBED_PROVIDER` environment variable changes. This avoids lock-in to any single provider as the free-tier landscape evolves.

```typescript
// src/lib/llm.ts
import { createGroq } from '@ai-sdk/groq'
import { createAnthropic } from '@ai-sdk/anthropic'
import { createGoogleGenerativeAI } from '@ai-sdk/google'
import { createOpenAI } from '@ai-sdk/openai'

export function getLLMModel() {
  const provider = process.env.ACTIVE_LLM_PROVIDER ?? 'groq'
  switch (provider) {
    case 'anthropic':
      return createAnthropic()('claude-sonnet-4-6')
    case 'google':
      return createGoogleGenerativeAI()('gemini-2.0-flash')
    case 'groq':
    default:
      return createGroq()('llama-3.3-70b-versatile')
  }
}

export function getEmbedModel() {
  const provider = process.env.ACTIVE_EMBED_PROVIDER ?? 'openai'
  switch (provider) {
    case 'voyage':
      return createOpenAI({ baseURL: 'https://api.voyageai.com/v1' })
               .textEmbeddingModel('voyage-3-lite')
    case 'openai':
    default:
      return createOpenAI().textEmbeddingModel('text-embedding-3-small')
  }
}

Usage pattern in any API route:

import { generateObject, generateText, embed } from 'ai'
import { getLLMModel, getEmbedModel } from '@/lib/llm'

const { object } = await generateObject({ model: getLLMModel(), schema: SkillSchema, prompt })
const { embedding } = await embed({ model: getEmbedModel(), value: profileText })

ETL Pipeline

The admin JD ingestion pipeline keeps the curriculum grounded in real job description requirements without requiring code deployments.

flowchart LR
    A[Admin pastes JD text] --> B[POST /api/admin/jd-ingestion-queue]
    B --> C[POST /api/extract-skills]
    C -->|generateObject with vocabulary constraint| D[LLM Provider]
    D --> E[Extracted skills preview]
    E --> F[Admin reviews in jd_ingestion_queue UI]
    F --> G[POST /api/confirm-extraction]
    G --> H[Approve + embed JD + update skill_frequency]
    H --> I[POST /api/aggregate-skill-frequency]
    I --> J[Recalculate frequency weights for slice]

The LLM extraction prompt includes the existing skill_frequency.skill_name vocabulary list. This constrains output to known taxonomy terms, preventing skill name fragmentation. New skills surface as outliers for admin review rather than auto-creating new vocabulary entries.

Nothing writes to the live curriculum until the admin explicitly approves at step F. At product scale, the inline API route is replaced by an AWS Batch job that returns a { jobId, status: 'queued' } response — the business logic is identical.

The migration runner tracks applied files in a migrations table and applies each in a transaction. It is safe to re-run — already-applied files are skipped.

// scripts/migrate.ts
import { neon } from '@neondatabase/serverless'
import { readFileSync, readdirSync } from 'fs'
import { join } from 'path'

const sql = neon(process.env.DATABASE_URL!)

async function migrate() {
  await sql`CREATE TABLE IF NOT EXISTS migrations (
    id SERIAL PRIMARY KEY,
    filename TEXT NOT NULL UNIQUE,
    applied_at TIMESTAMPTZ DEFAULT NOW()
  )`

  const applied = await sql`SELECT filename FROM migrations`
  const appliedSet = new Set(applied.map(r => r.filename))

  const files = readdirSync('./supabase/migrations').sort()
  for (const file of files) {
    if (appliedSet.has(file)) continue
    const sqlText = readFileSync(join('./supabase/migrations', file), 'utf-8')
    await sql.transaction(async tx => {
      await tx(sqlText)
      await tx`INSERT INTO migrations (filename) VALUES (${file})`
    })
    console.log(`Applied: ${file}`)
  }
}

migrate().catch(console.error)

Run with: npx tsx scripts/migrate.ts

Deployment

Vercel

Zero-config Next.js deployment. Connect the GitHub repo in the Vercel dashboard and set environment variables. Vercel ignores the Dockerfile and builds from source for personal phase deployments.

Neon

  1. Create a Neon project at neon.tech. Enable "no pausing" to prevent the database from suspending between sessions.
  2. Copy DATABASE_URL (connection string) to Vercel environment variables.
  3. Run migrations: npx tsx scripts/migrate.ts
  4. Run seed: npx tsx scripts/seed.ts

The Neon serverless driver (@neondatabase/serverless) uses HTTP — no connection pool configuration is needed in a serverless environment.

Clerk

  1. Create a Clerk application at clerk.com. Enable Google OAuth.
  2. Add CLERK_SECRET_KEY and NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY to environment variables.
  3. Wrap the root layout with <ClerkProvider>.
  4. Configure a webhook in the Clerk dashboard pointing to POST /api/webhooks/clerk, selecting the user.created event. The webhook handler provisions users, user_profiles, and subscriptions rows — replacing the Supabase handle_new_user trigger.
  5. Set admin role: Clerk Dashboard → Users → select user → publicMetadata: { "role": "admin" }.

Docker (for AWS ECS migration)

The Dockerfile is maintained from day one. Vercel ignores it during personal phase deploys. When migrating to AWS ECS Fargate, push the same image to ECR and configure a task definition — no application code changes required.

Key Design Decisions

Decision Reasoning
users.id is TEXT, not UUID Clerk user IDs have the format user_2abc... — not UUID-compatible. Storing them as TEXT is the only correct choice; all FK references to users.id are TEXT.
Application-level auth over RLS (V2a) Stripe subscription status is asynchronous; RLS cannot reliably enforce "has active subscription." Clerk JWT + WHERE user_id = $userId in every route is simpler and equally correct at personal scale. RLS policies are defined in migration 014 for product phase activation.
Vercel AI SDK over direct LLM APIs Provider-agnostic from day one. Switching from Groq to Anthropic, Google, or any future provider requires only an env var change — no code changes. Critical for a project whose LLM cost profile will evolve.
HNSW over IVFFlat for pgvector Better recall at K=25, supports incremental inserts without reindexing. IVFFlat requires a full reindex when new JDs are added — unacceptable for an admin-operated ETL pipeline.
Node.js migration runner over Supabase CLI Neon is not a Supabase project — the Supabase CLI cannot manage it. A Node.js runner using @neondatabase/serverless is self-contained, needs no local CLI, and runs in CI.
Groq as default LLM Free tier with generous rate limits and strong structured output on Llama 3.3 70B. The ACTIVE_LLM_PROVIDER abstraction means this can be changed without touching code when the free-tier landscape shifts.
Docker-first packaging Vercel personal deploy and AWS ECS Fargate product deploy use the same Docker image. Personal → product migration is a one-day infrastructure config task, not a code rewrite.
