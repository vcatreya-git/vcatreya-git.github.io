The problem

The navigation gap every aspiring PM faces

Every major PM prep platform teaches frameworks and interview techniques. None solves the upstream problem: direction.

🧭

Wrong direction

Platforms assume you know which PM role to target. An engineer wants to build products differently than a consultant moving into PM. A growth PM in fintech faces a different bar than one in consumer. Existing tools treat them identically — no archetype matching, no personalisation.

📊

No market-grounded readiness signal

Existing readiness scores use invented internal rubrics with no connection to what employers actually screen for. Candidates prepare in the dark — no feedback loop, no signal, just silence until they apply and get rejected without knowing why.

🗂️

No honest gate

There is no point at which the system tells you "you're ready." Bootcamp alumni confidently apply before they've shipped anything. Self-taught learners spend a year on case studies but never validate whether a company would care. PMRocket is that gate — grounded in real JD data.

Stage 2 — The match moment

Direction in 3 minutes

Sarah answers 15 questions during lunch. After 15 signals the system shows: Technical PM, 78% confidence. Reasoning displayed: strong technical depth, shipped code, but zero GTM experience — a gap, not a disqualifier.

"I finally know which direction to point."
Stage 4 — The evidence loop

Real proof, not invented

Over 3 months Sarah logs 13 artefacts — a shipped GitHub case study, an interview study as a Notion doc, a strategy memo from work. Her readiness score climbs from 22 to 61. Each log takes under 90 seconds and triggers a visible score bump.

"I'm building things that actually count."
Stage 5 — The readiness gate

An honest signal

At score 78 (above threshold of 75), with gap ≤ 30% and no critical missing skills, the system tells Sarah: ✓ You're ready to apply for Technical PM roles in developer tools. Not before. Not for Growth PM. For this specific role, with this evidence.

"I know I'm ready. And I know why."
Who it's for

Built for two distinct users

Every feature decision is defended through the lens of a specific persona. No feature creep from hypothetical users.

Primary · V1

The Wanderer

Aspiring PM, 3–6 months into self-directed preparation

Has read the books, watched the talks, built some case studies. Does not know if she is building the right things for the right role. Does not know when to start applying. PMRocket tells her: here is your archetype, here is what matters for your domain and market, here is what you still need.

Secondary · V2a

The Navigator

Existing PM levelling up, switching domain, or moving to a new market

Has proven she can do PM but needs to prove competence in a new area. PMRocket becomes a career progression tool — maps the specific gaps between where she is and where she wants to be, using real market data as the ground truth. Informed by existing seniority; retrieves only Senior PM JDs for gap analysis.

Technical depth

Under the hood

Production-grade design decisions at every layer — not a toy demo.

Weighted archetype matching

15-signal normalised scoring

score(A) = Σ[w(q,A) × raw(q,A,answer)] ───────────────────────────── Σ w(q,A)

Every intake answer is a scored signal for every PM archetype. Weights are stored in question_weights table — admin-configurable at runtime, no code deploy required. Q12 (technical skills, weight 9) decides ties within 0.02 of each other. Deterministic and market-grounded, not editorial.

pgvector HNSW gap analysis

JD-grounded readiness signal

HNSW (m=16, ef=64) → K=25 JD retrieval profile embed → cosine similarity → LLM narrative + gap_pct metric

On-demand, not auto-triggered. Gap analysis is hidden if fewer than 15 JDs exist for the user's archetype × domain × geography slice — the product never generates a signal from an insufficient corpus. gap_pct = (1 − evidenced / total) × 100 is deterministic and computed separately from the LLM narrative.

LLM abstraction layer

Provider-agnostic inference

ACTIVE_LLM_PROVIDER=groq|anthropic|google ACTIVE_EMBED_PROVIDER=openai|...

All LLM calls route through a factory pattern — getLLMModel() reads the env var and returns the appropriate Vercel AI SDK model instance. Groq (Llama 3.3 70B, free tier) is the default. Swap providers with one environment variable — zero code changes. Designed for Vercel → AWS Fargate portability from day one.

Admin ETL pipeline

Market-current curriculum ops

JD paste → PII strip → LLM extract → admin approve/reject per skill → embed → jd_embeddings → skill_frequency

Extraction is vocabulary-constrained — the LLM maps JD text to existing taxonomy terms and cannot introduce new skill names. Curriculum Signals panel surfaces Trending (high JD frequency, not in curriculum), Stable, and Declining skills. No code deployment required to tune the curriculum or reweight matching.
