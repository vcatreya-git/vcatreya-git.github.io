User Flows — Predictopia

Step-level flows with edge cases. Companion to User Journeys.

Diagrams: 04-sequence-predict.drawio · 05-sequence-scoring.drawio · journey maps 06 / 07

This page is the portfolio proof of interaction design under constraints: cutoff time, offline money, free API quotas, and senior-friendly mobile UX.

1. Hero flow — Admin creates pool

Goal: Pool exists with permanent invite link; prize rules transparent before anyone joins.

Step What the user sees What they do What happens
1 Landing / My Pools Taps Get Started or + Auth gate if needed (Google)
2 Onboarding (new users) Name, avatar, favourite team Saves users row; theme accents apply
3 Create Pool wizard — identity Pool name, optional icon Draft local state
4 Create Pool — money Buy-in (₹0 free), commission 0–50%, distribution tier Live prize preview recompute
5 Create Pool — league style Chunks / weekly / monthly / season Auto-generates competitions rows
6 Success Copies join link pools.join_code permanent URL
7 Pool Home Pins link in WhatsApp Role = creator; empty members

Key moments:
- Prize preview is the conversion confidence moment for paid pools.
- Permanent link is the anti-Sheets moment — no daily link generation.

Edge cases:
- Buy-in ₹0 → free pool; join is auto-approve
- Network fail mid-create → form data preserved, retry
- Duplicate names allowed (identity is pool UUID)

2. Member joins pool

Goal: Member is in the pool with correct money state; no leaderboard leak before conversion.

Step What they see What they do What happens
1 WhatsApp invite Taps link Deep link /pools/join/[code]
2 Auth Google sign-in Session cookie
3 Pool preview Confirms buy-in Name, icon, count, buy-in only
4a Free Join Taps Join Inserts pool_members active
4b Paid Request Taps Request Status pending
5 Waiting / Home — Admin approve → approved/active; mark paid → payment_status=paid

Key moments:
- Preview hides full LB (privacy + conversion).
- Approve ≠ Paid is intentional product design for async UPI/cash.

Edge cases:
- Already member → redirect Pool Home
- Pool full (100) → reject join
- Blocked user → cannot rejoin

3. Predict match (happy path + lock)

Goal: One-tap pick before cutoff; independent thinking; social reveal after.

Step What they see What they do What happens
1 Predict tab / Pool matches Opens today’s card Loads match + own prediction
2 Team A / Team B tiles Taps A POST prediction upsert
3 Selected state Optionally taps B Update same row (UNIQUE pool,user,match)
4 Countdown — Client shows time to cutoff_at
5 After cutoff Refresh / Realtime API returns all members’ picks grouped by team
6 Share card Shares to WhatsApp navigator.share + QR still works as invite

Key product rule: Enforcement is now() < cutoff_at in API routes — no toss-detection cron. Last write before cutoff wins.

Edge cases:
- After cutoff → 423 / locked UI
- Match abandoned → scoring awards 1 pt path later
- Offline → error toast, retry
- Advance picks: next 5 fixtures editable until each cutoff

4. Result + scoring loop

Goal: Fair points with thrifty external API usage.

Step What they see What they do What happens
1 Completed match Opens card Check match_results
2a Cache hit Winner shown — No external API
2b Cache miss Loading — Fetch CricketData → insert once (ON CONFLICT DO NOTHING)
3 Scores update — Recompute pool points, streaks, achievements
4 Leaderboard Opens tab Serve from leaderboard_cache (weekly / monthly / overall)

Key moments:
- First opener of a result pays the API cost for everyone (by design).
- Sync scoring at family scale — no job queue required.

5. Admin day-to-day (retention of the organiser)

Goal: Keep admin under 5 minutes/day so the pool survives 70 matches.

Step What they see What they do What happens
1 Admin → Requests Approve / reject Membership status
2 Admin → Payments Mark Paid payment_status
3 Pool Home share Share LB / nudge card Share sheet + QR
4 Result dispute Override winner source = admin_override
5 Budget Read-only view collected / allocated / paid / remaining

Out of daily path: re-entering scores, rebuilding sheets, chasing people with custom links.

6. Season prizes + settlement

Step What they see What they do What happens
1 Final LB — Freeze standings for period
2 Prize table Admin pays offline Nx formula amounts
3 Prize row Mark Paid History visible as winnings
4 Member history Views “Won ₹X” Never net-loss UI

7. Multi-pool switch (power user)

Step What they see What they do What happens
1 My Pools Opens pool A Context = A
2 Predict same fixture Picks Team A Row keyed by pool A
3 Switch to pool B Picks Team B Independent row for pool B
4 Leaderboards View each pool Streaks isolated

Key product rules encoded in flows

Rule Why Implementation surface
Permanent join link Zero daily link spam pools.join_code
Picks private until cutoff Independent thinking API visibility gate on cutoff_at
Approve ≠ Paid Real-world UPI lag status + payment_status
Never show net losses Family-friendly, non-gambling tone Member prize UI
Results on first open Stay within free API quota match_results first-write-wins
Multi-pool isolation Different social strategies Composite unique on predictions
Max 100 members Family/group scale, not public mega-pool Join reject at cap
No payment rails Regulatory + complexity boundary Offline mark-paid only

Failure modes designed for

Failure User experience System behaviour
Cricket API down at result time Card shows pending; admin can override Retry later; override path
Recursive RLS (historical) N/A after 007 Policies never self-query same table
Double join request Already member redirect Unique (pool_id, user_id)
Cutoff race Last accepted write before cutoff Server clock authoritative
Late join mid-season Clear policy late_join_policy on pool
